# Эталонный корпус: что есть, чего не хватает, как размечать

## Зачем отдельный корпус

Сохранённые чтения в `tests/fixtures/run-*.json.gz` — это то, что прочитал сам сайт. Ими проверяется логика сверки, но не качество OCR: движок нельзя оценивать по его же ответам. Эталон — текст, списанный с этикетки человеком, и вывод человека о том, совпадает ли раздел с Word.

## Что есть сейчас

Три листа, все от одного заказчика, все растр 300 dpi:

| Лист | Файл | Вид | Строк в эталоне | Разделов «совпадает» / «отличается» |
|---|---|---|---|---|
| Сябры. Чистая 0,7 л | `assets/sample.pdf` | PDF с вложенной картинкой | 55 | 14 / 0 |
| Сан Ремино. Розе 0,75 л | JPG | изображение | 34 | 6 / 6 |
| Сан Ремино. Дольче 0,75 л | JPG | изображение | 35 | 7 / 5 |

Разметка лежит в `desktop/bench/truth/*.json`. Она сделана ассистентом по увеличенным вырезам этикетки (не по увеличенному образцу на листе и не по Word) и **человеком не проверена** — поле `status: "provisional"`. Вердикты по разделам «Сябров» совпали с прежней независимой сверкой `tests/fixtures/sample-human-reference.json`.

## Каких выводов по такому корпусу сделать нельзя

- **Про векторные PDF — никаких.** Ни одного векторного файла в корпусе нет.
- **Про долю опасных ошибок.** Настоящих расхождений этикетки с Word в корпусе 11. Ноль ложных совпадений из 11 означает лишь, что истинная доля с вероятностью 95 % ниже примерно 24 % (1 − 0,05^(1/11)). Чтобы утверждать «ниже 1 %», нужно около 300 настоящих расхождений без единого пропуска.
- **Про другие шрифты, типографии и продукты.** Один заказчик, два узких гротеска, два вида техлиста.
- **Про «точность на будущих этикетках» в процентах.** Локальный метод к тому же отлаживался на этих же трёх листах — его цифры на них оптимистичны. Корпус для проверки должен быть отложенным: файлы, которые никто не видел во время разработки.

## План корпуса

Цель первой очереди — 40 листов, второй — 150. Каждый лист относится к одной или нескольким группам; в скобках минимум для первой очереди.

| Группа | Что проверяет | Минимум |
|---|---|---|
| Векторный PDF с живым текстом | текстовый слой, порядок чтения; OCR здесь почти не нужен | 6 |
| Векторный PDF с текстом в кривых | перерисовка крупнее действительно добавляет детали | 8 |
| PDF с вложенной картинкой | предел — разрешение картинки | 6 |
| JPG / PNG 300 dpi | основной растровый случай | 8 |
| JPG / PNG 150–200 dpi, сильное сжатие | где чтение разваливается | 4 |
| Мелкая кириллица до 1 мм | главный источник ошибок | в каждом втором листе |
| Повёрнутый текст (90°, 270°, 180°) | направление чтения | 8 |
| Сложный фон: выворотка, градиент, фото, фольга | контраст краски | 6 |
| Числа и знаки: Е-коды, проценты, телефоны, ГОСТ/СТБ, даты, штрихкоды | опасные ошибки | в каждом листе |
| Другие типографии и формы техлиста | выноски, поиск контура | 5 разных |
| Другие шрифты: антиква, рубленый нормальной ширины, рукописный | перенос на другие гарнитуры | 6 |
| Несколько этикеток на листе, фигурная высечка | выбор контура | 4 |
| Казахский, белорусский, английский рядом с русским | выбор модели чтения | 4 |
| **Листы с известными расхождениями с Word** | ложные совпадения | не меньше 15, см. ниже |

### Откуда взять расхождения

Настоящие расхождения редки, а именно на них измеряется опасная ошибка. Три источника, по убыванию ценности:

1. **Архив правок.** Версии макетов, которые возвращали типографии на исправление, вместе с тем Word, против которого их проверяли. Каждая такая пара — настоящее расхождение с известной причиной.
2. **Намеренно испорченные макеты.** Технолог меняет в копии векторного макета одну цифру, слово или знак (240 → 250, Е220 → Е224, «допускается хранить» → «хранить») и экспортирует как обычно. Это изменение самой этикетки, поэтому проверяется вся цепочка, включая OCR.
3. **Изменения в Word** при неизменной этикетке. Дёшево и делается автоматически (уже есть в `desktop/bench/score.mjs`, раздел «Опасная ошибка на управляемых изменениях Word»). Проверяет сверку при данном чтении, но не то, как OCR прочитает изменённую печать. Замена пунктам 1 и 2 — только частичная.

## Формат разметки

Один файл JSON на лист, схема `label-check.truth/1`:

```json
{
 "schema": "label-check.truth/1",
 "sheet": "rose",
 "kind": "image",
 "sourceDpi": 300,
 "page": 1,
 "annotator": "Фамилия И. О., дата",
 "status": "provisional",
 "verifiedBy": "",
 "label": {"x": 0.077, "y": 0.337, "w": 0.381, "h": 0.202},
 "tags": ["raster", "tinted-background", "condensed-type"],
 "excluded": "что намеренно не вошло в строки",
 "lines": [
  {"text": "СПИРТ 6,8 % САХАР 50 Г/Л ОБЪЕМ 0,75 Л", "rotation": 0, "tags": ["large", "numbers"]}
 ],
 "sections": [
  {"rule": "r5", "title": "Срок годности, условия хранения", "truth": "different",
   "differences": ["Word: 24 месяца, этикетка: 12 месяцев"]}
 ]
}
```

| Поле | Значение |
|---|---|
| `kind` | `image`, `raster-pdf` (PDF из одной картинки) или `vector-pdf`. Результаты считаются по этим группам раздельно |
| `sourceDpi` | разрешение пикселей, которые есть в файле; для вектора — `null` |
| `status` | `provisional` — размечено одним человеком или ассистентом; `verified` — второй человек сверил с оригиналом и вписал себя в `verifiedBy` |
| `label` | прямоугольник печатной этикетки в долях страницы; нужен только сценарию `grid.mjs` |
| `lines[].text` | строка в точности как напечатана: регистр, знаки, пробелы. Перенос слова остаётся переносом |
| `lines[].rotation` | на сколько градусов по часовой повернуть лист, чтобы строка читалась: `0`, `90` (текст идёт снизу вверх), `180`, `270` |
| `lines[].tags` | размер: `small` (прописная до 1,2 мм), `medium` (до 3 мм), `large`; содержимое: `numbers`; вид: `rotated`, `reversed`, `italic`, `latin`, `complex-background` |
| `sections[].rule` | идентификатор раздела, как его даёт разбор Word (`r0`, `r1`, …) |
| `sections[].truth` | `same` — на этикетке то же, что в Word (регистр и знаки препинания не в счёт, как и в приложении); `different`; `no-text` — в Word текст не задан; `graphics` — знак, не текст; `not-applicable` — в Word прочерк |
| `sections[].differences` | для `different` — каждое отличие словами: что в Word и что на этикетке |

## Правила разметки

1. Текст списывается **с печатной этикетки внутри контура**. Увеличенный образец рядом на листе и текст Word не источник: именно их отличие от этикетки и надо уметь находить.
2. Если знак нельзя разобрать на глаз при увеличении ×3 — строка получает тег `illegible`, а спорное место записывается как `?`. Такая строка в счёт ошибок не идёт: эталон не может быть увереннее человека.
3. Одинаковые по начертанию знаки (`ООО` и `000`, `BY` и `ВУ`) записываются по смыслу. Счёт «букв и цифр» их не различает, строгий — различает; обе цифры есть в отчёте.
4. Знаки, логотипы и цифры под штрихкодом в строки не входят и перечисляются в `excluded`.
5. Раздел `different`, если отличается хотя бы одно слово, число или единица. Другая запись той же величины (`г/л` вместо `г/дм³`) — тоже `different`, с пометкой в `differences`.
6. Разметку проверяет второй человек; до этого `status` остаётся `provisional`, и выводы по листу помечаются как предварительные.
7. Макеты заказчиков в репозиторий не кладутся. В `desktop/bench/corpus.json` файл указывается как `corpus:<имя>` и ищется в каталоге из переменной `LABEL_CORPUS_DIR`.
8. Не меньше пятой части корпуса откладывается: эти листы не открываются при разработке и используются только для итоговой оценки.

## Как добавить лист

1. Положить Word и макет в каталог корпуса, добавить запись в `desktop/bench/corpus.json`.
2. Запустить `npm run bench -- --sheets=<id>`; идентификаторы разделов взять из сохранённого `bench/out/<id>-baseline.json` (поле `rules`).
3. Заполнить `desktop/bench/truth/<id>.json`: строки — глядя на этикетку, разделы — сравнивая этикетку с Word.
4. `npm run score` пересчитает таблицы.
