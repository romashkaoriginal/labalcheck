# ADR: экспериментальная настольная версия для Windows

Статус: принято для эксперимента (spike), 10 октября 2026 года. Не решение о выпуске продукта: вывод «продолжать или нет» — в [RESULTS.md](RESULTS.md).

Документ описывает два шага. Сначала был сделан отдельный упрощённый локальный метод; замеры показали, что он хуже веб-версии. Затем локальный движок был подставлен под весь порядок чтения веб-версии — это и есть режим приложения по умолчанию (раздел «Второй шаг» ниже).

## Вопрос

Даст ли локальная обработка на компьютере пользователя измеримое улучшение точности OCR и сверки макетов по сравнению с веб-версией. Веб-версия при этом остаётся как есть и собирается прежними командами.

Сама настольная оболочка точность не меняет: те же пиксели, тот же код сверки. Прирост может дать только одно из трёх изменений, которые в браузере сделать труднее или нельзя:

1. **Другая модель поиска строк.** Веб-версия ищет строки моделью `PP-OCRv5_mobile_det` (4,8 МБ). Локально можно позволить `PP-OCRv6_medium_det` (62 МБ): в браузере её пришлось бы скачивать при каждом холодном старте и выполнять в один поток WASM.
2. **Другая модель чтения.** Вместо общей кириллической `cyrillic_PP-OCRv5_mobile_rec` (34 языка) — `eslav_PP-OCRv5_mobile_rec` (русский, белорусский, украинский, английский).
3. **Больше чтений за то же время.** Нативный ONNX Runtime в несколько потоков против WASM в один поток; у веб-версии второй движок видит этикетку, уменьшенную до 1800 пикселей по длинной стороне, из-за памяти WASM.

Чего локальная обработка **не** даёт: новых деталей на растре. Картинка 300 dpi остаётся картинкой 300 dpi; увеличение перед распознаванием — интерполяция.

## Что есть сейчас (по коду, а не по README)

Поток данных веб-версии, `src/app.js`:

1. **Требования.** `importDocx`: DOCX распаковывается (`fflate`), `word/document.xml` разбирается через `DOMParser`; таблицы и абзацы уходят в `parseRequirements` (`src/requirements.js`) → список разделов `{id, title, text, original, constraint}`.
2. **Страница.** PDF рисуется `pdf.js` в Canvas при масштабе `min(6, 6500 / длинная сторона)` — для A4 это 432 dpi; изображение берётся как есть. `pdfPicture` по списку операторов страницы определяет, не является ли PDF одной вложенной картинкой.
3. **Контур и масштаб.** `detectFrames`, `refineFrame`, `detectArtworkRegion` (`src/automatic.js`) ищут контур высечки по цвету; Tesseract читает лист целиком, `declaredLabelSize` и `resolveScale` (`src/scale.js`) сверяют заявленный размер этикетки с контуром.
4. **Чтение.** Tesseract.js читает этикетку многими проходами: целиком в четырёх поворотах, разреженно, по блокам (`segmentInk`), неоднозначные фразы крупнее (`refinementAreas`), каждую строку отдельно тремя способами (`seedBlocks`, `blockLines` из `src/lines.js`), места ненайденных слов (`edgePlaces`), количество и цифры. К словам добавляются текстовый слой PDF (`pass: 'pdf'`) и штрихкод по полосам (`scanEan13`). На трёх листах корпуса получается 27–34 прохода и около 2200 слов.
5. **Второй движок.** `src/secondary-ocr.js`: PaddleOCR (`@paddleocr/paddleocr-js`, ONNX Runtime Web, WASM, один поток) читает этикетку целиком — только если после Tesseract остались неуверенные фразы — и все вырезанные строки, расставленные на чистых листах (`lineSheets` из `src/paddle.js`).
6. **Объединение и сверка.** `assess` (`src/automatic.js`) → `matchRequirements` → `locatePhrase` (`src/phrase.js`); чтения второго движка подключает `fuseOcrMatches` (`src/ocr-fusion.js`); `settleEdges` учитывает перечитанные места.
7. **Размеры.** Высота букв — по пикселям символов Tesseract (`typicalHeight`), количество — `src/quantity.js`, выноски техлиста — `src/callouts.js`.
8. **Карточка и отчёт.** `evaluate` (`src/engine.js`) превращает совпадения в строки со статусами; `render` и `exportReport` показывают их.

Что можно использовать совместно, а что привязано к браузеру:

| Модуль | Canvas / DOM | Вывод |
|---|---|---|
| `engine.js`, `requirements.js`, `phrase.js`, `automatic.js`, `ocr-fusion.js`, `quantity.js`, `scale.js`, `barcode.js`, `lines.js`, `paddle.js`, `callouts.js` | нет: принимают массивы пикселей и слова | используются настольной версией напрямую, без копий |
| `secondary-ocr.js` | да: `document.createElement('canvas')`, `location.href` | привязан к браузеру |
| `app.js` | да: 101 обращение к DOM и Canvas; разбор DOCX, отрисовка PDF, весь порядок чтения (`recognize`, 270 строк) и интерфейс в одном файле без экспортов | переиспользовать можно только целиком, запустив страницу |

Главное следствие: **правила сверки уже отделены от браузера, а порядок чтения — нет.** Поэтому настольная версия запускает веб-версию целиком в рамке как базовый метод и не переписывает её конвейер.

Расхождения документации с кодом, найденные по пути:

- README: «При открытии страницы загружается образец». В коде `loadSample` при старте не вызывается (коммит `013c4f7`, «Start without bundled sample files»). `scripts/browser-run.mjs` без аргументов ждёт именно загруженного образца — этот путь, вероятно, устарел (запуском не проверял).
- README: второй движок «читает и всю этикетку, и каждую строку». По коду всю этикетку он читает, только если есть неуверенные фразы с покрытием от 70 %; иначе — одни строки.
- Модуль PaddleOCR веб-версии выполняет код из строк (`eval`) и не работает под политикой содержимого без `'unsafe-eval'`. В README этого нет; выяснилось при первом запуске в оболочке, где второй движок молча отключился.

## Сравнение оболочек: Tauri 2 и Electron

| Критерий | Tauri 2 | Electron 44 |
|---|---|---|
| Повторное использование UI | Страница работает в системном WebView2 (на Windows тоже Chromium, но той версии, что стоит у пользователя) | Страница работает в том Chromium, с которым собрано приложение; базовый метод ведёт себя как в Chrome, где он и проверялся |
| Локальный OCR-процесс | Отдельный исполняемый файл-«sidecar» (`bundle.externalBin`, запуск через `tauri-plugin-shell` с разрешением в capabilities) либо код на Rust. Модели PaddleOCR нужно запускать из Rust (`ort`) или упаковывать Python/Node отдельным бинарником | `utilityProcess.fork`: дочерний процесс Node.js, в нём `onnxruntime-node`. Тот же язык, что и весь проект; общие модули подключаются `import` |
| Упаковка моделей | Ресурсы приложения | Обычные файлы рядом с кодом |
| Размер | Маленькая оболочка (WebView2 системный); модели и sidecar добавляются сверху. Не измерял | Измерено: собранное приложение (`npm run package`) — 982 МБ. Из них лишнее: `onnxruntime-node` для чужих платформ (224 из 288 МБ) и два неиспользуемых детектора (93 МБ); нужное — Electron, `onnxruntime-node` win32-x64 64 МБ, выбранные модели 70 МБ, копия веб-версии 160 МБ |
| Память | Один WebView-процесс + sidecar. Не измерял | Измерено в [RESULTS.md](RESULTS.md): в покое 380–390 МБ на все процессы |
| Обновления | Плагин updater: подпись обязательна и не отключается, манифест на статическом хостинге, NSIS/MSI | `autoUpdater` (Squirrel) или `electron-updater`; подпись кода — на усмотрение разработчика |
| Безопасность обработки чужих PDF | Доступ страницы к системе закрыт по умолчанию, открывается явными разрешениями (capabilities) | Нужна ручная настройка: `contextIsolation`, `sandbox`, запрет навигации и сети (сделано, см. ниже). PDF разбирает `pdf.js` в песочнице страницы — в обеих оболочках одинаково |
| Сложность поддержки | Второй язык (Rust), набор сборки MSVC, отдельная сборка sidecar | Один язык. Цена — обновлять Electron вслед за исправлениями безопасности Chromium |
| Что нужно на этой машине | Rust и Build Tools не установлены | Достаточно `npm install` |

**Решение: Electron.** Причины по убыванию веса:

1. Эксперимент должен сравнить два метода на одном движке страницы. В Electron базовый метод работает в том же Chromium, что и в Chrome; в Tauri он оказался бы в WebView2 другой версии, и разницу в результатах пришлось бы отделять от разницы движков.
2. Локальный OCR пишется на том же JavaScript и берёт общие модули сверки без моста между языками. Для Tauri пришлось бы либо писать PaddleOCR-конвейер на Rust, либо собирать sidecar, — это работа над оболочкой, а не над вопросом эксперимента.
3. Размер сборки для инструмента, который ставят на рабочие места технологов, менее важен, чем срок и риск.

Если по результатам будет решено делать продукт, вопрос оболочки стоит открыть заново: граница «единый формат результата OCR» (ниже) от оболочки не зависит, и OCR-процесс можно вынести в sidecar Tauri без изменения сверки.

## Сравнение вариантов OCR

| Вариант | Что это | Лицензия | Решение |
|---|---|---|---|
| Tesseract.js 6 + `rus`/`eng` | Текущий первый движок, WASM | Apache-2.0 | Базовый метод, без изменений |
| PaddleOCR в браузере: `PP-OCRv5_mobile_det` + `cyrillic_PP-OCRv5_mobile_rec`, ONNX Runtime Web | Текущий второй движок, WASM, один поток | Apache-2.0 | Базовый метод, без изменений |
| **PaddleOCR локально: `PP-OCRv6_medium_det` + `eslav_PP-OCRv5_mobile_rec`, `onnxruntime-node` 1.30** | Те же семейства моделей в нативной среде | модели Apache-2.0 (карточки моделей PaddlePaddle), среда MIT | **Экспериментальный метод** |
| `PP-OCRv5_server_det` (88 МБ) | Серверный детектор прошлого поколения | Apache-2.0 | Измерен, отвергнут: на этих этикетках читает хуже мобильного (см. RESULTS) |
| Распознаватели PP-OCRv6 | 50 языков: китайский, английский, японский и 46 языков латиницы | Apache-2.0 | Не подходит: кириллицы в списке языков нет. Детектор PP-OCRv6 от языка не зависит и используется |
| Нативный Tesseract 5 + `tessdata_best` | Тот же движок без WASM | Apache-2.0 | Не измерялся: это ускорение того же чтения, а не новое чтение. Кандидат на следующий шаг |
| PaddleOCR на Python (sidecar) | Эталонная реализация с теми же моделями | Apache-2.0 | Отвергнут для прототипа: сотни мегабайт среды исполнения ради тех же моделей |
| EasyOCR, docTR | Python-библиотеки | Apache-2.0 | Не измерялись: требуют Python-среды; отдельного довода в их пользу для мелкой кириллицы нет |
| Surya 2 | Трансформер-OCR | код Apache-2.0, веса — модифицированная OpenRAIL-M с порогами по выручке и запретом конкуренции с Datalab (по сторонним описаниям, официальный текст не открывал) | Отвергнут до проверки лицензии юристом |
| PyMuPDF для отрисовки PDF | Быстрый нативный рендер | AGPL-3.0 | Отвергнут для поставки; в эксперименте использован только как инструмент для вырезов при разметке |

Модели скачиваются с хоста PaddlePaddle сценарием `desktop/scripts/fetch-models.mjs`; SHA-256 каждого архива закреплён в `desktop/models/manifest.json`. Точность моделей по документации PaddleOCR (на их собственных наборах): `eslav` 81,6 %, `cyrillic` 80,27 % строк без единой ошибки; `PP-OCRv6_medium_det` 86,2 против 75,2 у `PP-OCRv5_mobile_det`. Эти цифры получены не на этикетках и здесь ничего не доказывают — поэтому всё перемерено на своём корпусе.

```
┌──────────────────────── Electron ────────────────────────────────────────┐
│ главный процесс  src/main.mjs                                            │
│   · окно, протокол app://label-check/ (только файлы из desktop/build)    │
│   · запрет сети и навигации, отказ во всех разрешениях                   │
│   · запуск и остановка процесса OCR, пересылка заданий                   │
│        ▲ ipc (preload.cjs: recognize / cancel / progress)                │
│        │                                                                 │
│ страница (песочница, без Node)  renderer/                                │
│   · выбор файлов, отрисовка PDF (pdf.js), поиск контура                  │
│   · рамка «Проверка»: сайт с подставленными движками (lab.html)          │
│   · рамка «Веб-версия как есть»: сайт без изменений                      │
│   · сверка с Word: модули src/*.js веб-версии, одни и те же для обеих    │
│        │ пиксели RGBA                      ▲ строки и слова              │
│        ▼                                   │                             │
│ процесс OCR (utilityProcess)  src/ocr/worker.mjs → engine.mjs            │
│   · onnxruntime-node, модели из desktop/models                           │
│   · не читает файлы пользователя, не имеет сети                          │
└──────────────────────────────────────────────────────────────────────────┘
```

## Границы доступа к файлам

- Файлы пользователя попадают в приложение одним путём: стандартный выбор файла или перетаскивание в окно. Страница получает объект `File`; пути на диске она не видит.
- Главный процесс документы пользователя не открывает. Исключение — режим `--bench`: там он читает ровно два файла текущего листа из `bench/corpus.json` по роли («требования», «макет»); путь от страницы не принимается.
- Процесс OCR получает только пиксели. С диска он читает одни модели.
- Сеть закрыта: `session.webRequest.onBeforeRequest` отменяет любой запрос не к `app:`, `blob:`, `data:`. Навигация за пределы `app://label-check/`, новые окна и `<webview>` запрещены; запросы разрешений отклоняются.
- Страница оболочки работает с политикой содержимого без `'unsafe-eval'`. Страницы веб-версии в рамке получают `'unsafe-eval'`, потому что без него её PaddleOCR не работает (см. выше); наружу они при этом всё равно обратиться не могут.
- Ничего не сохраняется: результаты живут в окне до его закрытия, как и в веб-версии.

Чего прототип не делает: подпись кода, установщик, автообновление, журналирование. Чужой PDF разбирает `pdf.js` внутри песочницы Chromium; отдельной изоляции разбора нет.

## Обмен данными между интерфейсом и OCR

Граница между любым способом чтения и сверкой — один формат, `desktop/shared/ocr-result.mjs`:

```
{
  schema: "label-check.ocr-result/1",
  method, engine: {det, rec, runtime, passes},
  page:  {width, height},                         пиксели исходной страницы
  scale: {mmPerPixel, level, origin, sourcePixelMm},
  words: [{
    text,                                         как прочитано, без исправлений
    box: {x, y, w, h},                            пиксели исходной страницы
    rotation: 0 | 90 | 180 | 270,                 поворот по часовой, делающий текст прямым
    confidence: 0…100,
    source: "ocr" | "pdf-text" | "barcode",
    engine: "tesseract" | "paddle-web" | "paddle-local" | "pdf" | "barcode",
    pass, line
  }]
}
```

`sourcePixelMm` — размер пикселей, которые действительно есть в файле: у PDF с вложенной картинкой это шаг картинки, а не шаг отрисовки. `toAppWords` переводит формат в вид, который принимает `assess`; `fromAppWords` описывает тем же форматом чтения веб-версии. Обе стороны сравнения оцениваются из одного описания.

Текст из Word в OCR не попадает ни в каком виде: процесс OCR получает пиксели и возвращает прочитанное. Требования участвуют только в сверке и в выборе контура среди нескольких (по сумме покрытия — так же, как в веб-версии).

Транспорт: `ipcRenderer.invoke('ocr:recognize', {id, image, models, options})` → главный процесс → `utilityProcess.postMessage`. Пиксели копируются структурным клонированием: вырез этикетки — около 3 МБ, уменьшенный лист — до 15 МБ. Общая память не используется: выигрыш был бы в миллисекундах.

## Формат ошибок

Процесс OCR и мост возвращают ошибку объектом, а не строкой:

```
{ code, message, stage, retryable }
```

| `code` | Когда | `retryable` |
|---|---|---|
| `BAD_INPUT` | пустое или повреждённое изображение | нет |
| `MODEL_MISSING` | нет файла модели или списка символов (в сообщении — «npm run models») | нет |
| `RUNTIME_MISSING` | не установлен `onnxruntime-node` | нет |
| `OUT_OF_MEMORY`, `INFERENCE_FAILED` | среда выполнения отказала на шаге `detect` или `recognize` | да |
| `PROCESS_EXITED` | процесс OCR завершился во время задания | да |
| `CANCELLED` | отмена пользователем | нет |
| `INTERNAL` | всё остальное | нет |

`message` — текст для пользователя на русском; `stage` — `input`, `load`, `detect`, `recognize`, `process`. Ошибка одного метода не отменяет другой: карточка метода показывает сообщение, второй метод выполняется.

## Отмена

- **Процесс OCR.** Задание отменяется сообщением `ocr:cancel`. Процесс проверяет флаг между шагами (после поиска строк, между пачками строк при чтении) и отвечает `CANCELLED`. Если за пять секунд ответа нет, главный процесс завершает процесс OCR; следующий запуск создаёт его заново. Так отменяется упрощённый локальный метод.
- **Страницы проверки** (обе рамки). У веб-версии своей отмены нет, и её код не менялся. Кнопка «Отменить» перезагружает рамку: это завершает её рабочие потоки Tesseract и освобождает память. Задание, уже отданное процессу OCR, доработает до конца (секунды), его ответ отбрасывается. Настоящая отмена посреди проверки появится только вместе с выносом порядка чтения из `src/app.js`.

## Отвергнутые решения и причины

- **Переписать порядок чтения веб-версии под Node.** Дало бы один конвейер с подменяемым движком, но это 270 строк `recognize` с Canvas на каждом шаге; изменение работающего сайта ради эксперимента противоречит условию.
- **Подставить локальный движок внутрь веб-версии вместо её второго движка.** Потребовало бы править `src/app.js`. Вместо этого вариант посчитан по сохранённым чтениям без изменения сайта (в RESULTS — «Базовый + локальный»).
- **Запускать базовый метод во внешнем Chrome, а локальный — в оболочке.** Время и память тогда меряются разными способами в разных процессах.
- **Свой протокол с `net.fetch` по файлам.** Заменён чтением файла и явным MIME: так политика содержимого и тип WASM задаются в одном месте.
- **Минимальный прямоугольник произвольного наклона для найденных строк (как в эталонном PaddleOCR).** Взят прямой прямоугольник: печать на этикетках идёт вдоль сторон листа. Наклонный текст локальный метод прочитает хуже — в корпусе его нет, не измерено.

## Что упрощённый локальный метод не делает

Упрощённый метод (`renderer/local-pipeline.js`, в замерах — «Упрощ.») читает этикетку двумя проходами и не выполняет того, что веб-версия делает поверх чтения: вырезание строк по собственной краске, перечитывание мест ненайденных слов, отдельное чтение количества и цифр, выноски техлиста, измерение высоты букв. Он оставлен только для замеров: по результатам он хуже веб-версии.

## Второй шаг: порядок чтения сайта на локальном движке

**Решение.** Не писать второй конвейер, а подставить локальный движок под существующий. `src/app.js` обращается к OCR в двух местах: импортирует `createWorker` из `tesseract.js` и динамически загружает `./secondary-ocr.js`. Сборка настольной версии (`desktop/build.mjs`) собирает тот же `src/app.js` ещё раз, перенаправляя эти два импорта на `desktop/renderer/lab/tesseract.js` и `desktop/renderer/lab/secondary-ocr.js`. Сам `src/app.js` не меняется, сайт собирается как раньше. Получается страница `build/web/lab.html`: тот же интерфейс, те же проходы, вырезание строк, выноски и размеры, а кто читает — задаёт адрес: `?primary=local|tesseract&second=local|tesseract|web|none`.

**Как локальный движок встаёт на место Tesseract.** Сайт говорит с движком на языке Tesseract; подмена переводит в обе стороны и ничего не решает о тексте:

| Что просит сайт | Что делает локальный движок |
|---|---|
| режим страницы 3, 6, 11 (страница, блок, разреженный текст) | поиск строк и чтение; картинка уже повёрнута сайтом, поэтому ищутся только строки слева направо. Размер для детектора: 2000, 1600 и 1200 пикселей по длинной стороне |
| режим 7, 8 (одна строка, одно слово) | только чтение, без поиска строк: картинка и есть строка |
| `tessedit_char_whitelist` («0123456789.,») | модель выбирает только среди этих знаков |
| блоки → строки → слова → символы с рамками | блоки и строки собираются из найденных рамок (`readingOrder`); рамка символа — участок строки вокруг места, где модель его выдала, на всю высоту строки. По этим рамкам сайт своим кодом меряет высоту букв |
| уверенность слова и символа | переводится на шкалу Tesseract (`onTesseractScale`): пороги сверки (75, 80) подобраны под неё, а локальный движок при той же цифре ошибается чаще |

**Второй движок.** `lab/secondary-ocr.js` повторяет две функции оригинала и отдаёт их либо оригиналу (PaddleOCR в WASM), либо локальному процессу, либо Tesseract.js. Когда первым читает локальный движок, вторым мнением служит Tesseract.js: два движка разной природы. Ему, как и на сайте, картинки подаются растянутыми в полтора раза по ширине.

**Путь данных.** Страница проверки работает в рамке и своего моста не имеет; она вызывает `window.parent.desktop.recognize` и `.lines` окна-оболочки (тот же источник `app://label-check`). Дальше — тот же путь, что описан выше: главный процесс, процесс OCR. Задания процесс OCR выполняет по очереди.

**Окно.** Три вкладки: «Проверка» — страница `lab.html` с выбранными движками, полный интерфейс сайта; «Сравнение с веб-версией» — один файл через неё и через сайт как есть, результаты рядом; «Веб-версия как есть». Движки переключаются списком «Чтение»: «строгое» (локальный первым, Tesseract.js вторым — по умолчанию) и «спокойное» (Tesseract.js первым, локальный вторым). Почему по умолчанию «строгое» — в RESULTS.

**Цена решения.** Локальный движок получает картинки и проходы, подобранные под Tesseract (увеличение этикетки до 2800 пикселей, растяжение в полтора раза, бинаризация); часть из них ему не нужна или вредит. Убрать их можно только в `src/app.js`. Следующий шаг, если разработка продолжится, — вынести порядок чтения из `app.js` в модуль с подменяемым движком; подмена при сборке тогда станет не нужна.
